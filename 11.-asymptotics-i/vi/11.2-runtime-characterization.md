# 11.2 Đặc trưng thời gian chạy

Ta muốn _đặc trưng_ (characterize) thời gian chạy của hai thuật toán vừa xét — tức tìm một đại lượng thay thế (proxy) phản ánh tổng thể hiệu năng của từng thuật toán.&#x20;

Khi đặc trưng thời gian chạy, ta có hai mục tiêu:

* Chúng phải đơn giản nhưng chặt chẽ về mặt toán học.
* Chúng phải thể hiện rõ sự vượt trội của một thuật toán so với thuật toán kia, nếu thực sự có một thuật tốt hơn.&#x20;

{% embed url="https://www.youtube.com/watch?ab_channel=JoshHug&v=mRn8Z46psX8" %}

Ta đã cài đặt cả thuật toán ngây ngô và thuật toán tốt hơn bằng Java. Hàm `dup1` ứng với thuật toán ngây ngô; `dup2` ứng với thuật toán tốt hơn.

```java
// Naïve algorithm: compare everything
public static boolean dup1(int[] A) {  
  for (int i = 0; i < A.length; i += 1) {
    for (int j = i + 1; j < A.length; j += 1) {
      if (A[i] == A[j]) {
         return true;
      }
    }
  }
  return false;
}
```

```java
// Better algorithm: compare only neighbors
public static boolean dup2(int[] A) {
  for (int i = 0; i < A.length - 1; i += 1) {
    if (A[i] == A[i + 1]) { 
      return true; 
    }
  }
  return false;
}
```

### Kỹ thuật 1

Kỹ thuật đầu tiên ta xem xét để đặc trưng thời gian chạy là đo trực tiếp thời gian thực thi (tính bằng giây) bằng một chương trình client.&#x20;

Có vài cách:

* Dùng đồng hồ bấm giờ vật lý (không nên).
* Dùng lệnh `time` có sẵn trên Unix.
* Dùng Princeton Standard Library (thư viện chuẩn của Princeton), có lớp `stopwatch`.

Dùng bất kỳ phương pháp nào cũng sẽ cho thấy (với độ chính xác khác nhau, tùy có chọn đường đồng hồ vật lý hay không) rằng khi kích thước đầu vào tăng, `dup1` mất nhiều thời gian hơn để hoàn thành, còn `dup2` hoàn thành với tốc độ tương đối ổn định.

Có vẻ kỹ thuật 1 hoạt động khá tốt để đặc trưng thời gian chạy! Kết quả thí nghiệm dễ hiểu và dễ triển khai. Tuy nhiên, có vài nhược điểm nghiêm trọng khiến ta không dùng nó cho mọi thứ:

* Có thể mất _rất_ lâu mới chạy xong.&#x20;
* Thời gian chạy có thể thay đổi theo máy, trình biên dịch, dữ liệu đầu vào, v.v.&#x20;

Vì những lý do này, kỹ thuật 1 không đạt mục tiêu đặc trưng thời gian chạy. Nó đơn giản, nhưng không chặt chẽ về mặt toán học. Hơn nữa, sự khác biệt theo máy, trình biên dịch, đầu vào, v.v. có nghĩa là kết quả có thể không thể hiện rõ mối quan hệ giữa `dup1` và `dup2`.

### Kỹ thuật 2A

Thay vì đo thời gian chạy thực tế bằng đồng hồ, ta có thể đếm tổng số thao tác (_operations_) mà mỗi thuật toán thực hiện! Theo trực giác, thuật toán thực hiện ít thao tác hơn sẽ tốt hơn. Ta có thể cố định cùng một kích thước đầu vào `N` cho cả hai thuật toán rồi so sánh số lần các thao tác đó chạy.&#x20;

Áp dụng điều này cho thuật toán `dup1` với kích thước đầu vào `N=10000`:

```java
for (int i = 0; i < A.length; i += 1) {
  for (int j = i+1; j < A.length; j += 1) {
    if (A[i] == A[j]) {
       return true;
    }
  }
}
return false;
```

| Thao tác       | Số lần (với N=10000)                               |
| -------------- | ------------------------------------------------- |
| i = 0          | 1                                                 |
| j = i+1        | 1 (trường hợp tốt nhất) đến 10000 (trường hợp xấu nhất) |
| <              | 2 đến 50,015,001                                   |
| += 1           | 0 đến 50,005,000                                   |
| ==             | 1 đến 49,995,000                                   |
| truy cập mảng | 2 đến 99,990,000                                   |

Thao tác `i = 0` chỉ chạy một lần ngay đầu lời gọi hàm. `j = i+1` phức tạp hơn — trong trường hợp tốt nhất khi `A[0] == A[1]`, nó chỉ chạy một lần (hãy tự kiểm chứng!). Trong trường hợp xấu nhất, `j` được khởi tạo một lần cho mỗi giá trị `i` ở vòng lặp ngoài, nên tổng cộng khởi tạo 10000 lần.&#x20;

Khi đi sâu vào vòng lặp, việc tính chính xác từng số đếm ngày càng khó khăn. Ta sẽ chỉ ra sau rằng các con số chính xác không quan trọng đến vậy.&#x20;

Tóm lại kỹ thuật 2A: ta đã giải quyết vấn đề _độc lập với máy_ — khác máy thường không làm thay đổi tổng số thao tác (trong đa số trường hợp). Tuy nhiên, việc tính đủ số đếm cho từng loại thao tác rất tốn công. Ngoài ra, `N` ta chọn là tùy ý, và ta vẫn không biết thời gian chạy thực tế là bao lâu.&#x20;

### Kỹ thuật 2B

Ta có thể tránh phụ thuộc vào một `N` cụ thể bằng cách tính _số đếm theo ký hiệu_ (symbolic count), tức biểu diễn số đếm bằng biến đầu vào `N`. Với kỹ thuật này, ta bổ sung cột số đếm theo ký hiệu vào bảng:

| Thao tác       | Số đếm theo ký hiệu     | Số lần (với N=10000)                               |
| -------------- | -------------------- | ------------------------------------------------- |
| i = 0          | 1                    | 1                                                 |
| j = i+1        | 1 đến N               | 1 (trường hợp tốt nhất) đến 10000 (trường hợp xấu nhất) |
| <              | 2 đến (N² + 3N + 2)/2 | 2 đến 50,015,001                                   |
| += 1           | 0 đến (N² + N)/2      | 0 đến 50,005,000                                   |
| ==             | 1 đến (N² - N)/2      | 1 đến 49,995,000                                   |
| truy cập mảng | 2 đến N²-N            | 2 đến 99,990,000                                   |

Số đếm theo ký hiệu giúp ta hiểu **mức độ tăng của số thao tác** khi kích thước đầu vào lớn lên. Tuy nhiên, việc tính toán lại càng tốn công hơn! Và nó vẫn không cho biết thời gian chạy thực tế.
